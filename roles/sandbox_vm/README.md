# sandbox_vm

Shared implementation for the sandbox's VM lifecycle and Secret-backed SSH
access. This is a project-local role, not a published collection.

## Required inputs and credentials

The public playbooks preserve `vm_name` and `ocp_namespace` as inventory inputs.
They map to `sandbox_vm_name` and `sandbox_vm_namespace` in role defaults.
There is no default namespace: missing or invalid names fail before resource
operations.

Use the OpenShift API credential (`credential-ocp`) for every job. SSH identities
are generated by Create and retrieved from the namespace by guest jobs; a
separate AAP Machine credential or AAP API token is not required.

## Entry points

Public playbooks select a semantic `sandbox_vm_action`:

| Action | Outcome |
| --- | --- |
| `create` | Ensure SSH identity and public-key Secrets, provision VM, explicitly start it |
| `start` | Start the managed Manual-strategy VM and discover its address |
| `stop` | Stop the managed Manual-strategy VM |
| `delete` | Remove managed VM, DataVolume and Secrets; wait for PVC cleanup |
| `check_inventory` | Fail clearly if the selected VM is missing from saved inventory |
| `prepare_ssh` | Stage the stored key locally and wait for authenticated SSH |
| `cleanup_ssh` | Remove job-local key/known-hosts files |

`start` and `create` add a temporary `sandbox_created_vm` inventory group for
their public playbook's SSH-verification play. This does not update AAP's saved
inventory; the workflow must still sync `inventory-virt-sandbox`.

Guest jobs use the inventory plugin's `{namespace}-{name}` host format.
Their first, local play checks inventory so an empty inventory is not silently
reported as a successful guest job.
`prepare_ssh` refuses other hosts and must run before fact gathering. Wrap
guest operations in `block` / `always` so `cleanup_ssh` runs on task failures.
The role overrides the selected host's SSH identity, username and common SSH
arguments for this direct pod-network connection.

## Settings

See [`defaults/main.yml`](defaults/main.yml) for the complete interface.

| Setting | Default |
| --- | --- |
| `sandbox_vm_ssh_user` | `cloud-user` |
| `sandbox_vm_ssh_secret_name` | `<vm_name>-ssh` |
| `sandbox_vm_cloudinit_secret_name` | `<vm_name>-cloudinit` |
| `sandbox_vm_cpu_cores` | `1` |
| `sandbox_vm_memory` | `2Gi` |
| `sandbox_vm_disk_size` | `30Gi` |
| `sandbox_vm_source_name` | `rhel9` |
| `sandbox_vm_source_namespace` | `openshift-virtualization-os-images` |
| `sandbox_vm_ready_timeout` | `900` seconds |
| `sandbox_vm_ssh_timeout` | `300` seconds |

The original architecture, machine type, firmware, pod masquerade network and
sandbox scheduling toleration are retained. The fixed MAC and obsolete template
revision labels are omitted; the platform assigns the MAC, and project labels
identify managed resources.

The Sandbox requires an inline cloud-init `user` string and enforces `Manual`
for its idler. Full `userDataSecretRef` bootstrap was rejected in the real test.
Instead, a small user-only bootstrap is inline; `accessCredentials` / `noCloud`
injects the generated public key from `<vm_name>-cloudinit`. That Secret contains
only `data.key`, never a private key or an entire cloud-config document.
The `<vm_name>-ssh` identity Secret is never referenced by the VM.

## State, cleanup and limitations

- Key creation is conditional on Secret absence. Re-runs reuse the identity.
  Create deliberately starts a stopped VM; it is not a passive definition-only
  reconciliation.
- Temporary files create local changes on each job; successful re-runs are not
  promised to report zero Ansible changes.
- Secrets are not VM-owned garbage-collection dependents: they must survive
  retries and are explicitly removed by Delete. Deleting a VM through the
  console alone does not remove these Secrets.
- The role is not atomic. A failed run can leave managed resources behind;
  inspect the result and use Delete when appropriate. There is no automatic
  rollback that might destroy a previously existing VM or disk.
- Unmanaged name collisions are refused. Existing unmanaged lab VMs require
  an explicitly reviewed migration or a new VM name.
- Check mode is deliberately unsupported and fails before operations.
- Actual VM creation, key retrieval, guest access and cleanup still require the
  approved end-to-end test. Syntax checks alone do not establish these outcomes.
